Chapter3The Relational Data Model

1A Brief History — Why the Relational Model?

The relational model was introduced in 1970 by the English computer scientist Edgar F. Codd in his landmark paper “A Relational Model of Data for Large Shared Data Banks”. To appreciate the model’s design choices, it helps to understand the problems it was solving.

Before the relational model, databases were based on hierarchical (tree-shaped) and network (graph-shaped) models. These models forced application programmers to:

  • Know the physical layout of data — any change to file structure or storage required rewriting every application that touched that data. Codd called this physical data dependence.

  • Navigate the “Connection Trap” — to retrieve related data in network models, a programmer had to walk explicit pointer paths. Missing a pointer or traversing in the wrong direction produced wrong results silently.

  • Accept inconsistency — there was no mathematical foundation to define what “consistent” even meant, so the same fact could be stored contradictorily in different parts of the database.

Codd’s 1970 paper targeted three specific goals:

  • Data independence: Programs should work unchanged even when physical storage changes.

  • Resolving the Connection Trap: Data relationships should be expressed declaratively (by value), not by physical pointers.

  • Mathematical consistency: A sound basis — set theory and predicate logic — to define, query, and reason about data.

Key Takeaways

  • ⭐

    The key insight was to represent all data as tables of values

  • ⭐

    where relationships between tables are expressed by matching values (foreign keys) rather than by pointers. A query language can then declare what data is needed, not how to navigate to it — this is the foundation that SQL is built on.

1.1The Connection Trap

To understand the Connection Trap in legacy network databases (like the CODASYL model), imagine a database for a company with Employees, Projects, and Departments:

  • Department pointers link to Employees assigned to that department.

  • Employee pointers link to Projects that the employee works on.

  • Project pointers link back to the Department funding the project.

Where the "Connection Trap" Silent Errors Happen

Because there was no high-level query language like SELECT ... JOIN, the programmer had to write procedural code (in languages like COBOL) to manually move a database cursor through explicit pointer addresses step-by-step:

  • The programmer starts at Department ("Engineering").

  • They follow the owner-to-member pointer path down to Employee ("Alice").

  • They follow Alice's project pointer to find Project ("Mars Rover").

  • The Trap: The programmer assumes that because they traversed Engineering -> Alice -> Mars Rover, the Mars Rover project must be funded by Engineering.

However, Alice might work on a project funded by Marketing.

By navigating through the Employee-Project pointer chain instead of checking the explicit Department-Project funding pointer chain, the programmer silently associates the Mars Rover project with Engineering budget reports.

Why Codd’s Relational Model Solved This

Edgar F. Codd recognized that requiring programmers to act as human navigational paths meant business logic was tied directly to physical memory structures.

In a relational database, you eliminate pointer-walking entirely by joining on matching data values instead of memory pointers:

SELECT Department.Name, Employee.Name, Project.Name
FROM Department
JOIN Project ON Department.Dept_ID = Project.Funding_Dept_ID
JOIN Employee_Project ON Project.Project_ID = Employee_Project.Project_ID
JOIN Employee ON Employee_Project.Emp_ID = Employee.Emp_ID;

Here, the DBMS engine handles the physical navigation underneath, ensuring that missing or misdirected pointer paths are structurally impossible.

The Pain Point: What Breaks?

Because the applications had physical data dependence:

  1. Broken Offsets: Every program that reads salary now reads bytes 49–56 (which now contains part of the Phone and partial salary digits), producing corrupted data or crash errors.

  2. Cascading Code Changes: It wasn't just the payroll program that needed updating. Every application that ever touched the file—such as the performance review system, tax reporting software, and benefits portal—had to be modified, recompiled, and re-tested, even if those programs didn't use the Phone field at all.

  3. Storage Hardware Upgrades: Changing from magnetic tapes to disks, or changing disk block sizes, required modifying the low-level record-seeking routines written directly into application code.

How Codd’s Relational Model Solved It: Physical Data Independence

Edgar F. Codd introduced an abstraction layer that decoupled application logic from physical disk layout.

In a relational database:

  1. You execute ALTER TABLE Employee ADD COLUMN Phone VARCHAR(5);.

  2. Applications query data by attribute name, not by physical byte address.

  3. The DBMS handles where bytes live on disk behind the scenes. If a new column is added, or if the database administrator changes indexes or moves the file to a different storage disk, the existing SELECT queries continue to work without a single line of application code needing to be changed.

2Where Do Tables Come From?

Before we dive into the mathematical definition of tables, domains, and keys, we must answer a fundamental question: Where do the tables come from?

We don’t just invent tables randomly. We design them based on how we perceive the real world. This process starts with two core concepts: Entities and Relationships.

Database design is usually a three-step process:

  • Conceptual Design (The “What”): We create an abstract model of the real world. We identify the things that matter (entities) and how they are connected (relationships). This is often done using an Entity-Relationship (ER) diagram. This model is independent of any specific database software.

  • Logical Design (The “How”): We take our conceptual model and map it to a specific data model, such as the Relational Model. We define tables (relations), columns (attributes), keys, and constraints. This is the main subject of this chapter.

  • Physical Design (The “Where”): We implement our logical design on a specific Database Management System (DBMS) like MySQL, PostgreSQL, or Oracle, deciding on file organizations and indexes.

3Mathematical Backgound

3.1Set theory

📖Set theory

is a fundamental branch of mathematics that studies sets, which are well-defined collections of distinct objects called elements or members.

Tip

In computer science and database theory, set theory provides the mathematical foundation for how data is structured and queried.

Key Concepts in Set Theory:

  • 1. Elements and Membership: An object x is an element of a set A, written as x∈A. If x is not in A, it is written as x∈/A.

    • Example: A={1,2,3,4}. Here, 3∈A, but 5∈/A.

  • 2. Core Set Operations

    • Union (A∪B): Combines all unique elements from both sets.

      • {1,2}∪{2,3}={1,2,3}

    • Intersection (A∩B): Finds only elements shared by both sets.

      • {1,2}∩{2,3}={2}

    • Difference (A∖B or A−B): Finds elements in set A that are not in set B.

      • {1,2,3}−{2,3}={1}

    • Cartesian Product (A×B): The set of all ordered pairs (a,b) where a∈A and b∈B.

      • {1,2}×{X,Y}={(1,X),(1,Y),(2,X),(2,Y)}

  • 3. Essential Properties

    • Uniqueness: A set contains no duplicate elements (e.g., {1,1,2} is identical to {1,2}).

    • Unordered: The sequence of elements does not matter (e.g., {A,B}={B,A}).

3.2First-Order Predicate Logic (FOPL)

📖First-Order Predicate Logic (FOPL)

is a formal mathematical language used to express statements, reason logically, and determine truth values based on rules.

Tip

While propositional logic can only deal with simple declarative statements (e.g., "It is raining" = True/False), first-order logic breaks statements down into objects, properties, relationships, and quantifiers.

Key Components of First-Order Logic:

  • Objects (Constants): Specific entities in the domain of discourse (e.g., John, CS101, 5).

  • Variables: Symbols representing unspecified objects (e.g., x, y, z).

  • Predicates: Functions that express properties of objects or relationships between them and evaluate to True or False:

    • Property: IsStudent(x)

    • Relationship: EnrolledIn(x,y)

  • Functions: Expressions that map objects to another object (e.g., FatherOf(x)).

  • Logical Connectives: Standard operators to combine expressions:

    • AND (∧), OR (∨), NOT (¬), IMPLIES (→), IF AND ONLY IF (↔).

  • Quantifiers:

    • Universal Quantifier (∀): "For all" or "For every".

    • Existential Quantifier (∃): "There exists at least one".

📝

  • Natural English: "Every student enrolled in CS101 has passed a prerequisite."

  • First-Order Logic:

    ∀x(Student(x)∧EnrolledIn(x,CS101)→∃y(Prerequisite(y)∧Passed(x,y)))

4The Relational Model

Proposed by E. F. Codd in 1970, the relational model provides a formal framework for database systems grounded in set theory and first-order predicate logic. Data is represented declaratively as collections of relations (tables) rather than physical pointers.

4.1Core Concepts & Structural Architecture

Before diving into formal notation, it is essential to establish the structural hierarchy of a relational database, moving from global definitions down to the stored data state.

📖Database Schema (S)

Database Schema (S): Defines the entire database structure as a set containing all relation schemas {R1​,R2​,…,Rm​} along with the set of integrity constraints (IC) that govern them (such as Primary Keys, Foreign Keys, and Domain Constraints).

S=({R1​,R2​,…,Rm​},IC)

📖Relation Schema (R)

Relation Schema (R): The static logical definition of a single table, specifying its name, attributes, and domains:

R(A1​:D1​,A2​:D2​,…,An​:Dn​)

📖Relation Instance

Relation Instance (r(R)): The dynamic snapshot of actual data stored in a relation at a given point in time:

r(R)={t1​,t2​,…,tm​}where each ti​∈D1​×D2​×⋯×Dn​

4.2Mathematical Definition

A relation R of degree (arity) n is defined mathematically as a subset of the Cartesian product of n domains:

R⊆D1​×D2​×⋯×Dn​

Where:

  • Domain (Di​): A set of atomic (indivisible) values of the same type.

    • DSalary​={x∈R∣x≥0}

    • DGender​={’M’,’F’}

  • Degree (n): The number of attributes (columns) defining the relation schema.

  • Cardinality (∣R∣): The total number of tuples (rows) present in the relation instance.

4.3Formal Tuple Notation

Each element of a relation R is an n-tuple t:

t=(v1​,v2​,…,vn​)where vi​∈Di​

Referencing Tuple Components

  • Index-Based Notation:

    t[i]=vi​

  • Attribute-Name Notation:

    t[Ai​]ort.Ai​

  • Sub-tuple (Projection) Notation:

    For a subset of attributes X⊆{A1​,A2​,…,An​}:

    t[X]

4.5.1Data Type

Databases provide support for different types of data and their variants:

  • INTEGER:- Whole numbers (e.g., 1, 42, -17)

  • FLOAT/ DECIMAL - Real numbers with decimal points.

  • VARCHAR/ TEXT - Character strings.

  • DATE- Calendar dates.

  • BOOLEAN- True/False values.

  • ENUM- Enumerated list of values

4.5.2Length / Precision

Length means the number of characters or digits that an attribute value has.

  • For VARCHAR(50): Maximum 50 characters.

  • For DECIMAL(10,2): Total 10 digits, 2 after decimal point.

  • For CHAR(6): Exactly 6 characters (e.g., PIN code).

4.5.3Date Format

A date contains day, month, and year in combination:

  • DD/MM/YYYY - 07/02/2026 (European format)

  • MM/DD/YYYY - 02/07/2026 (American format)

  • YYYY-MM-DD - 2026-02-07 (ISO 8601 standard)

4.5.4Range

A range is specified by lower and upper bounds of data values:

  • GPA: [0.0, 4.0]

  • Age: [0, 150]

  • Percentage: [0, 100]

  • Temperature: [-273.15, ∞) (Celsius, above absolute zero)

4.5.5Constraints

Particular conditions that put restrictions on allowed values:

  • NOT NULL - Value must be provided

  • UNIQUE - No duplicates allowed

  • CHECK - Custom validation rule

  • PRIMARY KEY - Uniquely identifies each row

  • FOREIGN KEY - References another table

4.6Keys and Integrity Constraints

While the mathematical definition of a relation (Section 5.2) tells us how data is structured, it does not tell us how to ensure the data is accurate, unique, and meaningfully connected. To enforce business rules and prevent data anomalies, the relational model relies on Keys (to identify records) and Integrity Constraints (to enforce rules).

4.6.1Keys: Identifying Tuples

In the real world, we identify entities by unique characteristics (e.g., a person by their National ID, a book by its ISBN). In the relational model, we use Keys to uniquely identify tuples (rows) within a relation.

Note

Keys are used to uniquely identify tuples (rows) within a relation.

4.6.1.1Super Key

📖Super Key

A set of one or more attributes (columns) that uniquely identifies a row (tuple) within a table. Any combination of columns that prevents duplicate rows is a super key.

Mathematical Definition

Let RR be a relation schema. A set of attributes SK⊆R is a super key if, for any valid state r(R), no two distinct tuples t1 and t2​ can have the same values for SKSK.

  • Equation:∀t1​,t2​∈r(R),(t1​=t2​)⟹t1​[SK]=t2​[SK]

where:

  • r(R): A valid state (instance) of the relation schema R.

  • t1​,t2​: Two distinct tuples (rows) within the relation state r(R).

  • SK: The set of attributes that form the super key (SK⊆R).

  • t[SK]: The projection (values) of tuple t on the set of attributes SK

Examples from the Table Above

1. Single-Attribute Super Keys

These columns are naturally unique by themselves:

  • {Student_ID}: Every student has a unique university ID number.

  • {National_ID}: Every student has a unique national ID number (رقم الهوية).

  • {Email}: Every university email address is unique.

2. Composite Super Keys (Supersets)

A Super Key remains a Super Key even if you add extra, unnecessary attributes to a unique key:

  • {Student_ID,Name}: Unique because Student_ID is already unique.

  • {National_ID,Department}: Unique because National_ID is already unique.

  • {Email,Name,Department}: Unique because Email is already unique.

  • {Student_ID,National_ID,Email,Name,Department}: The entire relation schema is also a valid Super Key.

3. NOT Super Keys

These attributes cannot uniquely identify a row:

  • {Name}: Fails because two different students share the same name ("Ahmed Khalil").

  • {Department}: Fails because multiple students belong to "Computer Science".

  • {Name,Department}: Fails if two students named "Ahmed Khalil" ever enroll in the same department.

4.6.1.2Candidate Key

📖Candidate Key

A Candidate Key is a minimal Super Key. It has the exact same unique identification property as a Super Key, but it contains no redundant attributes. If you remove any attribute from a Candidate Key, it ceases to be a key.

Mathematical Definition

A set of attributes CK⊆R is a Candidate Key for a relation schema R if and only if it satisfies the following two conditions:

  1. CK is a super key.

  2. Removing any attribute A from CK results in a set X=CK∖{A} that is no longer capable of uniquely identifying every tuple (it ceases to be a Super Key).

4.6.1.3Primary Key

📖Primary Key

The specific candidate key chosen by the database designer to uniquely identify each row in the table. It must contain unique values and cannot contain NULL values.

Mathematical Definition

A set of attributes PK⊆R is a Primary Key for a relation schema R if and only if for every valid relation state r(R), it satisfies:

1. Uniqueness (Super Key Property)

∀t1​,t2​∈r(R),(t1​=t2​)⟹t1​[PK]=t2​[PK]

2. Entity Integrity Constraint (Non-Null Property)

∀t∈r(R),∀A∈PK,t[A]=NULL

(If PK consists of a single attribute PK={A}, this simplifies to ∀t∈r(R), t[PK]=NULL.)

Why Staff_ID​ is a Valid Primary Key:

  1. Uniqueness (Super Key Property): Every employee has a unique Staff_ID (101, 102, 103, 104). No two distinct rows share the same ID.

  2. Entity Integrity (Non-Null Property): Every employee is guaranteed to have a Staff_ID. No row has a NULL value for this attribute.

Because both conditions are strictly satisfied across the relation, Staff_ID​ safely serves as the Primary Key.

Illustrating the Email Case (Why NULL Invalidates a Primary Key)

Even if all non-null email addresses are unique, Email fails as a Primary Key due to the following mathematical and logical violations:

1. Violation of the Entity Integrity Constraint

By definition, a Primary Key PK must satisfy:

∀t∈r(R),t[PK]=NULL

In this table, for tuple t3​ (Dr. Omar Khalid) and tuple t4​ (Layla Suleiman):

t3​[Email]=NULL
t4​[Email]=NULL

Because t3​[Email]=NULL, the Entity Integrity Constraint is broken.

2. Loss of Row Identification

In relational theory, NULL represents an unknown or missing value. Because Email is missing for both t3​ and t4​, the database cannot use Email to distinguish Dr. Omar Khalid from Layla Suleiman.

3. Failure of Mathematical Equality

In standard relational calculus and SQL three-valued logic, NULL = NULL evaluates to UNKNOWN (not TRUE). Therefore, testing uniqueness on NULL attributes fails the formal condition:

∀t1​,t2​∈r(R),(t1​=t2​)⟹t1​[PK]=t2​[PK]

Practical Takeaway

  • Staff_ID remains the valid Primary Key (Staff_ID​) because it is both unique and strictly non-null (=NULL) for every tuple.

  • Email can only be classified as an optional attribute or a candidate attribute with a sparse/filtered unique index, but it can never be a Primary Key whenever NULL entries exist.

Extending the Concept: Alternative (Alternate) Keys

In our FACULTY_DIRECTORY table, National_ID is also a completely valid Candidate Key because it is both unique for every single faculty member and guaranteed to never be NULL (∀t∈r(R), t[National_ID]=NULL).

However, standard relational theory dictates that a relation schema R can have exactly one Primary Key (PK).

Definition: Alternate (or Alternative) Key

Any Candidate Key that is not chosen by the database designer to be the Primary Key is called an Alternate Key (or Secondary Unique Key).

Mathematical Relation

Alternate Keys=Candidate Keys∖{Primary Key}

Applied Example

From our pool of valid Candidate Keys for the faculty directory:

Candidate Keys={{Staff_ID},{National_ID}}

  1. Primary Key (PK): We select Staff_ID​ to serve as the main entity identifier.

  2. Alternate Key (AK): National_ID becomes the Alternate Key.

4.6.1.4Foreign Key

📖Foreign Key

An attribute or set of attributes in one table that references the primary key (or candidate key) of another table, establishing a logical link and maintaining referential integrity between them.

Mathematical Definition

Let R1​ and R2​ be two relation schemas (where R1​ and R2​ can be the same relation in a self-reference), and let PK be the Primary Key of R2​.

A set of attributes FK⊆R1​ is a Foreign Key in R1​ referencing R2​ if it satisfies two conditions for every valid relational database state db={r(R1​),r(R2​)}:

1. Domain Compatibility

Dom(FK)=Dom(PK)

(The attributes in FK have the same domain/data type as the primary key PK of R2​. If FK and PK are composite, there must be a one-to-one mapping between their corresponding attributes).

2. Referential Integrity Constraint

∀t1​∈r(R1​),(∃t2​∈r(R2​)such thatt1​[FK]=t2​[PK])∨(t1​[FK]=NULL)

Key Properties:

  • Referencing vs. Referenced: R1​ is called the referencing relation, and R2​ is the referenced relation.

  • Nullability: Unlike Primary Keys, Foreign Key attributes can contain NULL values (unless explicitly constrained by a NOT NULL constraint), representing an unassigned or missing relationship.

  • Self-Referencing Foreign Key: When R1​=R2​, the foreign key references its own table's primary key (e.g., Super_ssn referencing Ssn within an EMPLOYEE relation).

4.6.2Integrity Constraints (ICs)

📖Integrity Constraints

Integrity Constraints are business rules applied to the relational schema to ensure the accuracy and consistency of the data. If a database state violates an integrity constraint, it is considered an invalid state.

4.6.2.1Domain Constraints

These are the most basic constraints. They ensure that every attribute value must belong to its defined domain (data type, format, and range).

  • Rule: Values must match the specified data type and fall within allowed ranges.

  • Example: If the domain of Age is defined as integers between 18 and 100, inserting a value of 150 or 'Twenty' violates the domain constraint.

4.6.2.2Key Constraints & Entity Integrity

This constraint governs the Primary Key. Because the Primary Key's entire purpose is to uniquely identify a row, it must always have a value.

  • Rule (Entity Integrity): No part of a Primary Key can be NULL.

  • Example: You cannot insert an employee into the EMPLOYEE table without an Emp_ID. If Emp_ID is NULL, the database cannot uniquely identify or reference that specific employee.

  • Note: Uniqueness is also enforced (no two rows can have the same PK), which is inherently guaranteed by the definition of a Primary Key.

4.6.2.3Referential Integrity

This constraint governs Foreign Keys. It ensures that relationships between tables remain consistent. You cannot have an "orphan" record pointing to a non-existent parent.

  • Rule: A Foreign Key value must either be completely NULL (meaning the relationship doesn't exist yet) OR it must exactly match an existing Primary Key value in the referenced table.

  • Example: If the DEPARTMENT table only has departments ENG, MKT, and HR, you cannot insert an employee with Dept_Code = 'FIN'. The database will reject the insertion to maintain referential integrity.

4.7Formal Schema Notation

In database literature and practice, there are two primary ways to express a relational schema:

  1. The Strict Formal Notation (The Elmasri & Navathe academic standard).

  2. The Shorthand Relational Notation (The practical, inline design standard).

4.7.1Style 1 — The Strict Formal Notation (Elmasri & Navathe Style)

This notation is used in pure database theory. It strictly separates the structural definition of the tables from the Integrity Constraints (ICs). It focuses on the mathematical state of the database, not the procedural actions of the DBMS.

The 5 Rules of Strict Formal Notation:

  • Domains are Mandatory: Every attribute must be followed by a colon and its domain (data type).

    • Format:R(A1:D1, A2:D2, ...)

  • Primary Keys are Underlined: The primary key attribute(s) are denoted by a solid underline. If it is a composite key, every attribute in the key is underlined.

    • Format:R(A1​, A2, ...)

  • Foreign Keys are NOT Marked Inline: Foreign keys are written as normal attributes inside the parentheses. Their status as foreign keys is declared only in the Integrity Constraint (IC) list below the schema.

  • Integrity Constraints (ICs) are Listed Separately: All rules regarding Foreign Keys (Referential Integrity), NOT NULL, and CHECK constraints are written sequentially below the relation as IC1, IC2, IC3...

  • Referential Integrity uses Subset Notation: Foreign keys are expressed using the subset symbol (⊆).

    • Format:R1.FK_Attribute⊆R2.PK_Attribute

4.7.2The Shorthand Relational Schema Notation

This notation is used in practical database design, logical modeling, and university exams where writing out domains and massive IC lists is too time-consuming. It brings the structural relationships inline with the attributes.

The 4 Rules of Shorthand Notation:

  • Drop the Domains: Data types (:String, :Integer) are omitted to save space.

  • Keep Primary Keys Underlined: The solid underline for Primary Keys (simple and composite) remains exactly the same as the formal style.

  • Bring Foreign Keys Inline: Foreign keys are denoted using an inline arrow (→) or inline subset (⊆) directly after the attribute name, pointing to the referenced table and primary key.

    • Format:FK_Attribute→REFERENCED_TABLE(PK_Attribute)

  • Composite Foreign Keys use Parentheses: If multiple attributes form a composite foreign key, wrap them in parentheses before the arrow.

    • Format:(FK1, FK2)→REFERENCED_TABLE(PK1, PK2)

5The ER-to-Relational Mapping Algorithm

The Entity-Relationship (ER) model is a conceptual tool used to design a database from a business perspective. However, a DBMS cannot execute an ER diagram. To implement the database, we must translate (map) the conceptual ER model into a logical Relational Schema (tables).

This translation follows a strict, step-by-step algorithm. If followed correctly, the resulting relational schema will inherently satisfy Third Normal Form (3NF), preventing data redundancy and update anomalies.

5.1Regular (Strong) Entities and Simple Attributes

The Rule: Map each strong entity type to a relation (table). Include all simple attributes. Choose one of the candidate keys as the Primary Key (PK).

  • Composite Attributes: Flatten them. Include only the primitive sub-attributes as separate columns.

  • Derived Attributes: Discard them. They are computed on the fly in SQL and never stored as columns.

✅ Show Solution

Note

Address is flattened into Street, City, Zip. Age is dropped.

5.2Weak Entities

The Rule: Map the weak entity to a new relation. The Primary Key of this new relation is the Composite Key consisting of the owner entity's PK + the weak entity's partial key (discriminator). Include the owner's PK as a Foreign Key (FK).

The Rule: Multivalued attributes cannot be mapped as a single column (violating 1NF). Create a new relation to represent it. The PK of this new relation is the combination of the owning entity's PK and the multivalued attribute itself.

5.4Mapping Relationships, Relationship Attributes, and Participation

When translating an Entity-Relationship (ER) diagram into a Relational Schema, the cardinality (1:N, 1:1, M:N) dictates the structural mapping (where tables and foreign keys go). However, the participation constraint (Total vs. Partial) dictates the integrity constraints (specifically, whether a Foreign Key can be NULL).

  • Total Participation (Double line in ER): Every instance of the entity must exist in the relationship. (e.g., "Every order must have a customer").

  • Partial Participation (Single line in ER): An instance of the entity may or may not exist in the relationship. (e.g., "A customer may or may not have placed an order").

Below are the comprehensive rules and cases for mapping all binary relationship scenarios, including how to handle relationship attributes.

5.4.1Case 1: 1:N Relationship (Partial Participation on N-side) + Rel Attribute

Rules to Apply:

  • Structural Rule: Add the 1-side PK as a Foreign Key in the N-side table.

  • Attribute Rule: Place the relationship attribute in the N-side table.

  • Constraint Rule: Because the N-side is Partial, the FK may or may not have a value (it is nullable).

The Structural Rule: Use the Foreign Key approach. Take the Primary Key of the "1-side" (parent) entity and add it as a Foreign Key attribute in the "N-side" (child) entity's relation. Relationship attributes are also placed on the N-side.

The Participation Impact:

  • Partial Participation on the N-side: The Foreign Key in the N-side table is allowed to be NULL.

    • Example: An EMPLOYEE may or may not be assigned to a DEPARTMENT. The Dept_ID FK in EMPLOYEE is nullable.

  • Total Participation on the N-side: The Foreign Key in the N-side table cannot be NULL. You must add a NOT NULL constraint to the FK.

    • Example: Every ORDERmust belong to a CUSTOMER. The Cust_ID FK in ORDER is NOT NULL.

  • Total Participation on the 1-side: This does not change the FK placement, but it implies a business rule: every record in the 1-side table must be referenced by at least one record in the N-side table. (This is typically enforced by application logic, as standard SQL lacks a direct "must be referenced by at least one child" constraint).
