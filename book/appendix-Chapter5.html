2.4Solution: Normalization

Normalization is the process of decomposing a table into smaller, well-structured tables to:

  • Eliminate redundancy — the same data isn’t stored multiple times unnecessarily

  • Avoid anomalies — relationships between tables are clear and logical

  • Ensure data integrity — queries run faster and are easier to maintain

Note

When you perform ER-to-Relational Mapping, following standard mapping rules automatically structures your tables to be in at least 3NF in the vast majority of cases:

  • Entities → Tables: Each entity type becomes a separate relation, giving entity attributes a clear home around a chosen entity key.

  • Relationships → Foreign Keys or Junction Tables: Binary 1:N relationships use foreign keys, and M:N relationships become separate junction tables (e.g., Enrollments), which naturally isolates composite key attributes like Grade.

  • Attributes → Atomic Fields: Multi-valued attributes are broken out into separate tables, satisfying 1NF.

3Functional Dependencies

Before we can normalize, we need a precise language for describing what determines what in a relation. That language is Functional Dependencies (FDs).

In database design, FDs provide the formal mathematical foundation used to capture real-world business rules about how attributes relate to one another.

Think of an FD like a deterministic mathematical function:

y=f(x)⟹knowing x always gives you exactly one y

The database equivalent is written X→Y and reads:

"For every valid instance of X, there is a unique value of Y in the table."

In other words, for any two tuples (rows) t1​ and t2​ in a relation state r(R):

if t1​[X]=t2​[X], then t1​[Y]=t2​[Y]

If two rows share the same X value, they must share the same Y value—no exceptions.

📖Functional Dependency

A Functional Dependency X→Y (read as "X functionally determines Y") holds in a relation R if, for any valid state of R, whenever two tuples agree on the attributes of X, they must also agree on the attributes of Y.

  • Determinant: The left-hand side (X).

  • Dependent: The right-hand side (Y).

3.1Why FDs Are Essential

Without functional dependencies, you cannot formally define keys or prove that a design is free of data anomalies. FDs drive the entire theoretical foundation of relational database design:

  1. Functional Dependencies (X→Y): Formally define attribute-level constraints based on domain semantics (e.g., StudentID→StudentName).

  2. Keys (Super & Candidate Keys): Derived directly from FDs by computing attribute set closures (X+). A set X is a superkey if X+=R, and a candidate key if X is also minimal.

  3. Normal Forms (1NF→2NF→3NF→BCNF): Evaluated strictly by testing conditions on FDs and keys:

    • 2NF: Eliminates partial dependencies (Non-Prime⊂Candidate Key).

    • 3NF: Eliminates transitive dependencies (Non-Prime→Non-Prime).

    • BCNF: Ensures that for every non-trivial FD X→Y, X must be a superkey.

📝Attribute-Level Determinism

A company assigns each employee a unique employee number (EmpNo) or Social Security Number (SSN).

SSN→Name

  • Meaning: If you know the value of SSN, you can uniquely identify the Name of that employee.

  • Reading the Notation: The expression SSN→Name is read as:

    "SSN determines Name" or "SSN functionally implies Name."

Does the Reverse Hold (Name→SSN)?

Name→SSN× (False)

No. It would violate database consistency if two distinct employees happened to share the same name (e.g., two employees named "Ahmed"). Because their SSN values would be different, Name cannot uniquely determine SSN.

FDs Come from Domain Knowledge, Not Data Snapshots

Functional dependencies are constraints on the relation schema itself, derived from real-world business rules—not from a temporary snapshot of data:

  • × Do not infer an FD just because it happens to hold in the current rows of a table.

  • ✓ An FD is valid only if it holds for every possible valid state the database could ever enter.

3.2.1FD Validation

An Functional Dependency (FD) X→Y is valid (holds) in a relation state r(R) if and only if for every pair of tuples (rows) t1​ and t2​ in r(R) that agree on the attribute set X, they must also agree on the attribute set Y.

Formally:

X→Y⟺∀t1​,t2​∈r(R),if t1​[X]=t2​[X], then t1​[Y]=t2​[Y]

3.3Keys, Prime, and Non-Prime Attributes

3.3.1Review of Keys

📖Key Attribute

An attribute that uniquely identifies each entity instance.

📖Super Key

A set of one or more attributes (columns) that uniquely identifies a row (tuple) within a table. Any combination of columns that prevents duplicate rows is a super key.

📖Candidate Key

A Candidate Key is a minimal Super Key. It has the exact same unique identification property as a Super Key, but it contains no redundant attributes. If you remove any attribute from a Candidate Key, it ceases to be a key.

📝Candidate Keys vs. Super Keys

Suppose we have a relation R(SSN,Name,Address,Phone) with the functional dependency:

SSN→{Name,Address,Phone}

Key Classifications

  1. Candidate Key: {SSN}

    • Closure: {SSN}+={SSN,Name,Address,Phone}=R (it uniquely identifies all attributes in the relation, so it is a superkey).

    • Minimality: No proper subset of {SSN} can uniquely identify the entire relation. Therefore, {SSN} is a candidate key.

  2. Superkey (Not a Candidate Key): {SSN,Name}

    • Closure: {SSN,Name}+={SSN,Name,Address,Phone}=R (it uniquely identifies all attributes, so it is a superkey).

    • Minimality Check: It contains a proper subset, {SSN}, which is already a superkey on its own. Because Name is redundant for uniqueness, {SSN,Name} fails the minimality requirement and is not a candidate key.

Core Concept Breakdown

Candidate Key=Superkey+Minimality

  • Superkey: Any attribute set X whose closure covers the entire relation schema (X+=R).

  • Candidate Key: A minimal superkey—removing any attribute from X causes X+=R.

3.3.2Prime vs. Non-Prime Attributes

This distinction is critical for 2NF and 3NF normalization.

  • Prime Attribute: An attribute that is a member of ANY Candidate Key.

  • Non-Prime Attribute: An attribute that is NOT a member of any Candidate Key.

📝Candidate Keys & Attribute Classification

For a relation R(A,B,C,D) with candidate keys CK1​={A,B} and CK2​={B,C}:

  • Prime Attributes: {A,B,C}

    An attribute is prime if it is a member of at least one candidate key.

    • A∈CK1​

    • B∈CK1​ and B∈CK2​

    • C∈CK2​

  • Non-Prime Attribute: {D}

    An attribute is non-prime if it does not belong to any candidate key.

3.4Deriving Keys and Functional Dependencies

In database design, we are rarely handed all functional dependencies in their final form. We typically start with a set of known business rules F and must derive implied dependencies to analyze schema properties, verify rules, and discover candidate keys.

3.4.1Armstrong’s Axioms (The Inference Rules)

To derive new, sound, and complete functional dependencies from a given set F, we use Armstrong’s Axioms. The set of all possible FDs that can be logically inferred from F is called the closure of F, denoted as F+.

3.4.1.1Primary Axioms

  • Reflexivity: If Y⊆X, then X→Y.

    (A set of attributes always determines any of its subsets.)

  • Augmentation: If X→Y, then XZ→YZ for any attribute set Z.

    (Adding the same attributes to both sides preserves the dependency.)

  • Transitivity: If X→Y and Y→Z, then X→Z.

    (Functional determination propagates across intermediate attributes.)

📝

Imagine a university table tracking student enrollments with columns: StudentID, CourseID, and Semester.

  1. Given Set (X):

    • Let X={StudentID, CourseID, Semester}

  2. Choose a Subset (Y⊆X):

    • Let Y={StudentID}

  3. Result (X→Y):

    • Since Y is a subset of X, we get:

      {StudentID, CourseID, Semester}→{StudentID}

Intuition: If you already know the specific combination of a student, course, and semester, you inherently know the student's ID. Knowing the whole collection of attributes guarantees you know any individual part (or combination of parts) within that collection.

📝

  1. Given Functional Dependency (X→Y):

    • Knowing a product's barcode (X) determines its unit price (Y).

    • Barcode→Price

  2. Add Attribute Z to Both Sides (XZ→YZ):

    • Let Z={StoreLocation}.

    • Augmenting both sides with the store location gives:

      {Barcode, StoreLocation}→{Price, StoreLocation}

Intuition: If a barcode determines a price, then knowing the barcode and the store location will determine the price and that same store location.

📝

Imagine a corporate database tracking employee assignments with columns: EmployeeID, DeptID, and BuildingNo.

  1. Given Functional Dependencies:

    • Knowing an employee's ID determines their department ID (X→Y):

      EmployeeID→DeptID

    • Knowing the department ID determines the building where that department is located (Y→Z):

      DeptID→BuildingNo

  2. Result (X→Z):

    • By transitivity, we can chain these together to conclude that knowing the employee's ID indirectly determines their building:

      EmployeeID→BuildingNo

Intuition: If X leads to Y, and Y leads to Z, then X transitively leads to Z because Y acts as a bridge.

3.4.1.2Secondary (Derived) Rules

From the three primary axioms, we derive practical helper rules:

  • Union (Additive): If X→Y and X→Z, then X→YZ.

  • Decomposition: If X→YZ, then X→Y and X→Z.

  • Pseudotransitivity: If X→Y and WY→Z, then WX→Z.

📝Union (Additive) Rule

Given Functional Dependencies:

  • Knowing an EmployeeID determines their Name:

    EmployeeID→Name

  • Knowing the same EmployeeID determines their Email:

    EmployeeID→Email

  • Result (X→YZ):

    • By the Union rule, knowing the EmployeeID allows you to determine both together:

      EmployeeID→{Name, Email}

Intuition: If one key can look up your name and the same key can look up your email, you can group them into a single lookup for both pieces of information.

📝Pseudotransitivity Rule

Given Functional Dependencies:

  • Knowing a StudentID (X) determines their current Major (Y):

    StudentID→Major

  • Knowing a Major (Y) combined with a specific CourseLevel (W) determines the maximum AllowedCredits (Z):

    {Major, CourseLevel}→AllowedCredits

  • Result (WX→Z):

    • By Pseudotransitivity, we can substitute Major with StudentID, meaning knowing the student's ID and the course level gives you the allowed credits:

      {StudentID, CourseLevel}→AllowedCredits

Intuition: Since X provides Y, you can feed X into the second rule wherever Y is required, bridging X and W together to reach Z.

3.4.2Practical Tips for Spotting Keys Quickly

Before running any algorithm, experienced database designers use these visual heuristics to immediately narrow down the search for candidate keys. These tips come from analyzing the left-hand side (LHS) and right-hand side (RHS) of the given FDs.

Tip 1: The "Must-Have" Rule (Never on RHS)

Any attribute that never appears on the right-hand side of any FD must be part of every Candidate Key. Why? Because there is no way to derive this attribute from any other attribute. The only way it can appear in a closure is if you include it in the starting set.

Tip 2: The "Never a Key" Rule (Only on RHS)

Any attribute that only appears on the right-hand side (and never on the left-hand side) of any FD can never be part of any Candidate Key. Why? Because this attribute is always "determined by" something else. It adds no determining power. Including it in a key would make the key non-minimal.

Tip 3: The "Both Sides" Rule

Attributes that appear on both the LHS and RHS of various FDs are the "candidate" attributes. They might be part of a candidate key, depending on closure computation.

Tip 4: Single-Attribute Quick Check

Before trying combinations, always compute the closure of each individual "Must-Have" attribute and each "Both Sides" attribute. If any single attribute's closure equals R, that attribute alone is a Candidate Key.

3.4.3The Attribute Closure Algorithm

Computing the full set of all dependencies F+ can be exponentially large. To determine whether a specific set of attributes X can uniquely identify the entire table—or to test if a specific FD X→Y holds—we compute the Attribute Closure of X, denoted as X+.

📖The attribute closure

The attribute closure X+ is the set of all attributes in R that are functionally determined by X under the given set of dependencies F.

Algorithm: Computing Attribute Closure

  1. Initialization: Set X+=X.

  2. Iterative Expansion: Repeatedly search F for an FD A→B such that A⊆X+ and B⊈X+. If found, set X+=X+∪B.

  3. Termination: Repeat Step 2 until a full pass over F yields no new attributes (a fixpoint is reached).

📝Basic Step-by-Step Expansion

Given:

Relation Schema: R(A,B,C,D,E,F)

Functional Dependency Set F:

1.2.3.4.​A→B{B,C}→DD→EE→F​

Compute the attribute closure of {A,C}, denoted as {A,C}+.

✅ Show Solution

  • Initialization:

    {A,C}+={A,C}

  • Iteration 1:

    • Check A→B: LHS A⊆{A,C}+. Add B.

      {A,C}+={A,B,C}

    • Check {B,C}→D: LHS {B,C}⊆{A,B,C}+. Add D.

      {A,C}+={A,B,C,D}

    • Check D→E: LHS D⊆{A,B,C,D}+. Add E.

      {A,C}+={A,B,C,D,E}

    • Check E→F: LHS E⊆{A,B,C,D,E}+. Add F.

      {A,C}+={A,B,C,D,E,F}

    Termination:

    {A,C}+={A,B,C,D,E,F}=R.

Conclusion: Since {A,C}+ contains all attributes of R, {A,C} is a superkey. Because neither A+={A,B} nor C+={C} covers R, {A,C} is also a candidate key.

3.4.4The Complete Key-Finding Algorithm

This is the systematic procedure to find all Candidate Keys, classify Prime and Non-Prime attributes, and enumerate all Super Keys.

Step 1 — Classify all attributes into three groups:

  • Group M (Must-Have): Attributes that never appear on the RHS of any FD. These must belong to every Candidate Key.

  • Group N (Never-a-Key): Attributes that only appear on the RHS (never on the LHS). These can never be part of any Candidate Key.

  • Group B (Both-Sides): Attributes that appear on both LHS and RHS across different FDs.

Step 2 — Compute the closure of M:

  • Compute M+ using the attribute closure algorithm.

  • If M+=R, then M is the only Candidate Key. Stop.

  • If M+=R, proceed to Step 3.

Step 3 — Find Candidate Keys by extending M:

  1. Systematically add attributes from Group B to M, one at a time, then in pairs, and so on.

  2. For each combination, compute the attribute closure.

  3. If the closure equals R (i.e., X+=R), you have found a Super Key.

  4. Check Minimality: Test each attribute in your Super Key by trying to remove it. If removing any attribute still results in a closure of R, then the attribute was redundant, meaning the set is not minimal and therefore not a Candidate Key.

  5. Never add attributes from Group N, as they cannot help form a minimal key.

Step 4 — Identify Prime and Non-Prime attributes:

  • Prime Attribute: Any attribute that appears in at least one Candidate Key.

  • Non-Prime Attribute: Any attribute that appears in no Candidate Key.

Step 5 — Enumerate all Super Keys (if needed):

  • Every Candidate Key is automatically a Super Key.

  • Every superset of a Candidate Key is also a Super Key.

  • The Complete Set of Super Keys: All possible unions of Candidate Keys combined with any combination of Non-Prime attributes (along with combinations with each other).

(Note: We can skip larger pairs like {A,D,C} because they would contain the valid Candidate Key {A,C} as a subset, making them non-minimal).

Step 4: Classify Prime and Non-Prime Attributes

AttributeIn CK {A,C}?In CK {B,C}?Classification
A✅ Yes—Prime
B—✅ YesPrime
C✅ Yes✅ YesPrime
D❌ No❌ NoNon-Prime
E❌ No❌ NoNon-Prime

  • Prime Attributes: {A,B,C}

  • Non-Prime Attributes: {D,E}

Step 5: Enumerate All Super Keys

Every Candidate Key is a Super Key, and every superset of a Candidate Key is also a Super Key. To find all Super Keys, we take our Candidate Keys ({A,C} and {B,C}) and append all possible combinations of the Non-Prime attributes ({D,E}):

  1. Supersets of {A,C}:

    • {A,C} (Candidate Key)

    • {A,B,C} (Added B)

    • {A,C,D} (Added non-prime D)

    • {A,C,E} (Added non-prime E)

    • {A,B,C,D} (Added B,D)

    • {A,B,C,E} (Added B,E)

    • {A,C,D,E} (Added D,E)

    • {A,B,C,D,E} (Added all)

  2. Supersets of {B,C} (Unique additions):

    • {B,C} (Candidate Key)

    • {B,C,D} (Added non-prime D)

    • {B,C,E} (Added non-prime E)

    • {B,C,D,E} (Added D,E)

  • Complete Unique Set of All Super Keys (12 total):

    SK={{A,C},{B,C},{A,B,C},{A,C,D},{A,C,E},{B,C,D},{B,C,E},{A,B,C,D},{A,B,C,E},{A,C,D,E},{B,C,D,E},{A,B,C,D,E}}

💡 The Pattern: Notice that every Super Key contains either {A,C} or {B,C} as a subset. The Non-Prime attributes {D,E} act as "passengers"—appending them to any Candidate Key creates a valid Super Key, but they contribute no determining power of their own.

📝

Consider a relation schema R(A,B,C,D,E) with the following set of functional dependencies F:

F={A→BC,CD→E,B→D,E→A}

Find all candidate keys of the relation R.

✅ Show Solution

we need to find the attribute sets whose closure includes all attributes {A,B,C,D} and no proper subset has the same property.

Step 1: Identify Essential Attributes

Let's analyze which attributes appear on the right-hand side (RHS) versus the left-hand side (LHS) of the FDs:

  • RHS attributes:A,B,D

  • LHS-only / Missing from RHS:C never appears on the right side of any functional dependency. Because C is never generated by any FD,C must be part of every candidate key.

Step 2: Test Attribute Closures Including C

Since C must be in every candidate key, we start by testing combinations of C with other attributes.

1. Try C alone:

  • C+={C} (Does not include A,B,D) → Not a key.

2. Try two-attribute combinations containing C:

  • AC+:

    • Start:{A,C}

    • Apply AC→D: Add D→{A,C,D}

    • Apply AD→B: Add B→{A,B,C,D}

    • Result:{A,B,C,D} (All attributes!)

    • Check for minimality: Since neither A+ nor C+ alone gives all attributes,AC is a candidate key.

  • BC+:

    • Start:{B,C}

    • Apply BC→A: Add A→{A,B,C}

    • Apply AC→D (since we now have A and C): Add D→{A,B,C,D}

    • Result:{A,B,C,D} (All attributes!)

    • Check for minimality: Since neither B+ nor C+ alone gives all attributes,BC is a candidate key.

  • CD+:

    • Start:{C,D}

    • Apply CD→B: Add B→{B,C,D}

    • Apply BC→A (since we now have B and C): Add A→{A,B,C,D}

    • Result:{A,B,C,D} (All attributes!)

    • Check for minimality: Since neither C+ nor D+ alone gives all attributes,CD is a candidate key.

Conclusion

The candidate keys for relation R are:

  1. AC

  2. BC

  3. CD

3.5Types of Functional Dependencies

Not all functional dependencies are created equal. Some represent structural flaws (anomalies) in the database design, while others are mathematically trivial. Understanding these types is the exact mechanism used to define Second Normal Form (2NF) and Third Normal Form (3NF).

Table 30:Types of FDs
TermMathematical DefinitionMeaning & Impact
Trivial FDX→Y where Y⊆XAlways true by definition. Carries no new information.
Non-trivial FDX→Y where Y⊆XThe meaningful FDs that define actual business rules.
Full FDX→Y and no proper subset of X determines YThe ideal state. Y depends on the whole key.
Partial FDX→Y and a proper subset of X determines YRed flag for 2NF. Y depends on only part of a composite key.
Transitive FDX→Y→Z (where Y→X)Red flag for 3NF. Z depends on a non-key attribute.

3.5.1Trivial Functional Dependency

📖Trivial Functional Dependency

An FD X→Y is trivial if Y is a subset of X (Y⊆X).

📝

Consider an employee table where we know both the employee's ID and their name.

  • FD: {EmpID,Name}→EmpID (Since EmpID is part of the left-hand side set, this is trivial).

EmpIDNameDepartment
101AhmedComputer Science
102MahmoudEngineering

If you already know that an employee has ID 101 and is named Ahmed, stating that {EmpID,Name} determines EmpID tells you nothing new. You already had the ID.

3.5.2Non-Trivial Functional Dependency

📖Non-Trivial Functional Dependency

An FD X→Y is non-trivial if Y is not a subset of X (Y⊆X). If X and Y share no common attributes at all, i.e., X∩Y=∅, it is called completely non-trivial).

📝

Consider an employee table:

  • FD: EmpID→Department (Knowing the employee ID uniquely determines their department).

EmpIDNameDepartment
101AhmedComputer Science
102MahmoudEngineering

The attribute on the right (Department) is completely separate from the left (EmpID). This is a genuine business rule used to design the database.

3.5.3Full Functional Dependency

📖Full Functional Dependency

An FD X→Y is a full functional dependency if it is non-trivial, and removing any attribute A from X breaks the dependency (meaning no proper subset of X determines Y).

📝

Imagine a university enrollment relation where a student takes a course across a specific semester. The Primary Key is a composite key: {StudentID,CourseID}.

  • FD: {StudentID,CourseID}→Grade

StudentIDCourseIDGrade
201 (Ahmed)CS101A
201 (Ahmed)MATH202B
202 (Sara)CS101A

Can you know Ahmed's Grade by looking at StudentID alone? No, because Ahmed takes multiple courses with different grades. Can you know the Grade by looking at CourseID alone? No, because many students take CS101 and get different grades. Grade requires both attributes together to be uniquely determined.

3.5.4Partial Functional Dependency

📖Partial Functional Dependency

An FD X→Y is a partial dependency if a proper subset of X can already determine Y.

📝

Using the same enrollment table, suppose we also store the student's name:

  • FD: {StudentID,CourseID}→StudentName

StudentIDCourseIDStudentName
201CS101Ahmed
201MATH202Ahmed
202CS101Sara

  • The Red Flag: StudentName depends only on StudentID, which is just a proper subset of the composite key {StudentID,CourseID}.

  • The Problem: If Ahmed changes his name, you have to update it across multiple rows. If you miss one, your database becomes inconsistent. This violates 2NF, and the fix is to move StudentName into a separate table where StudentID is the sole primary key.

3.5.5Transitive Functional Dependency

📖Transitive Functional Dependency

An FD X→Z is transitive if there is an intermediate attribute set Y such that X→Y and Y→Z (where Y→X, and Y is not a candidate key).

📝

Consider an employee table where EmpID is the primary key:

  • FD 1: EmpID→DeptID (An employee belongs to a department ID)

  • FD 2: DeptID→DeptName (A department ID determines the department name)

  • Transitive FD: EmpID→DeptName (Through DeptID)

EmpIDNameDeptIDDeptName
101AhmedD01IT
102KhaledD02HR
103YousefD01IT

  • The Red Flag: DeptName is a non-prime attribute, but it depends on DeptID, which is also a non-prime attribute (just a regular column, not a candidate key for this table).

  • The Problem: If Department D01 changes its name from IT to Computer Science, you have to update every single employee belonging to that department. This violates 3NF, and the fix is to extract department data into its own table (DEPARTMENT).

4Normalization

Normalization is the systematic approach of effectively designing a database so that it minimizes data redundancy and inconsistency. It is generally done through a series of steps called Normal Forms (NF).

Each normal form builds on the previous one—a relation in a higher NF automatically satisfies all lower NFs:

1NF⊂2NF⊂3NF⊂BCNF⊂4NF⊂5NF

Diagram 56:Hierarchy of Database Normal Forms
Normal FormKey RequirementWhat it Eliminates
1NFAll attribute values are atomicMulti-valued / repeating groups
2NF1NF + no partial FDs on any candidate keyRedundancy from partial dependencies
3NF2NF + no transitive FDs (with prime-attr exception)Transitive dependencies via non-key attributes
BCNFEvery FD determinant is a superkeyAll non-trivial FD-based redundancy
4NFBCNF + no non-trivial MVDsMulti-valued dependency redundancy
5NF4NF + no non-trivial join dependenciesDecomposition artifacts

Before applying normalization rules, it is essential to understand where database tables originate. Tables in a normalized relational system typically come from one of two design paths:

4.2First Normal Form (1NF)

A relation is in 1NF if:

  • Every attribute contains only atomic (single-valued, indivisible) values

  • There are no repeating groups or multi-valued attributes

  • There is a primary key that uniquely identifies each row

📝Violating 1NF

Consider an unnormalized student table where a student can enroll in multiple courses, and those courses are stored together inside a single comma-separated cell:

StudentNoStudentNameCourses
S1AhmedDS, Algorithms
S2HusseinDatabases
✅ Show Solution

The Issue: The Courses attribute is not atomic because it holds multiple values in a single cell. This directly violates 1NF and prevents standard relational querying (like indexing or joining on individual course identifiers).

To bring the relation into 1NF, we split the multi-valued field into separate rows so that each cell holds exactly one atomic value:

StudentNoStudentNameCourseNoCourseName
S1AhmedCS101Data Structures
S1AhmedCS102Algorithms
S2HusseinCS301Databases

  • Atomicity Achieved: Each cell now holds a single, indivisible value.

  • Primary Key: The composite key {StudentNo,CourseNo} uniquely identifies each row in the flattened relation.

Note on Redundancy

While this table is now successfully in 1NF, the StudentName attribute is repeated for student S1. This structural redundancy is systematically addressed by moving to Second Normal Form (2NF).

4.3Second Normal Form (2NF)

A relation schema R is in Second Normal Form (2NF) if and only if:

  • It is already in 1NF.

  • Every non-prime attribute is fully functionally dependent on every candidate key.

Understanding Partial Dependencies

  • Scope: 2NF is only relevant when a relation has a composite primary key (composed of two or more attributes). A relation with a single-attribute primary key is automatically in 2NF if it is already in 1NF.

  • Partial Dependency: This occurs when a non-prime (non-key) attribute is functionally dependent on only a proper subset of a composite candidate key, rather than the entire key.

Second Normal Form eliminates these partial dependencies by breaking them out into separate relations.

📝Violating 2NF

Consider the 1NF student enrollment table where the composite key is StudentNo,CourseNo:

StudentNoStudentNameCourseNoCourseNameInstructorNoGrade

S1AhmedCS102AlgorithmsI2B+
S2HusseinCS301DatabasesI3A-

Functional Dependencies Present:

  • StudentNo,CourseNo→Grade (Full Dependency: both attributes are required to determine the grade).

  • StudentNo→StudentName (Partial Dependency: StudentName depends only on StudentNo, not on CourseNo).

  • CourseNo→CourseName,InstructorNo (Partial Dependency: course attributes depend only on CourseNo, not on StudentNo).

✅ Show Solution

4.4Third Normal Form (3NF)

A relation schema R is in Third Normal Form (3NF) if and only if it is already in 2NF and, for every non-trivial functional dependency X→A, at least one of the following conditions holds:

  • X is a superkey of R.

  • A is a prime attribute (i.e., A is a member of some candidate key of R).

Core Rules & Key Concepts

  • Eliminates Transitive Dependencies: A transitive dependency occurs when a non-key attribute determines another non-key attribute, forming a chain like Key→Y→Z (where Y is not a superkey and Z is a non-prime attribute). 3NF systematically removes these structures to prevent update anomalies.

  • The Prime Attribute Exception: Unlike Boyce-Codd Normal Form (BCNF), 3NF permits a non-key attribute to appear on the right-hand side of a dependency as long as that attribute belongs to a candidate key. This specific rule allows 3NF to preserve functional dependencies during decomposition where BCNF might otherwise fail.

📝Violating 3NF

Suppose we have a Courses relation schema that extends our 2NF design by also embedding instructor details:

Courses(CourseNo,CourseName,InstructorNo,InstructorName,InstructorLocation)

  • Candidate Key: {CourseNo}

  • Functional Dependencies:

    1. CourseNo→{CourseName,InstructorNo} (Key determinant)

    2. InstructorNo→{InstructorName,InstructorLocation} (Transitive dependency)

Why It Violates 3NF

  • The functional dependency InstructorNo→{InstructorName,InstructorLocation} features a determinant (InstructorNo) that is not a superkey of the relation.

  • Furthermore, the attributes on the right-hand side are non-prime attributes (they do not belong to any candidate key).

  • This creates a transitive chain: CourseNo→InstructorNo→{InstructorName,InstructorLocation}.

✅ Show Solution

To bring the relation into 3NF, we decompose it by extracting the transitive dependency into its own relation:

  1. Courses Table (Key: CourseNo)

    • Retains core course information and references the instructor via a foreign key.

CourseNoCourseNameInstructorNo
CS101Data StructuresI1
CS102AlgorithmsI2
CS301DatabasesI1

  1. Instructors Table (Key: InstructorNo)

  • Isolates attributes that depend directly on the instructor identifier.

InstructorNoInstructorNameInstructorLocation
I1Dr. AliBuilding A
I2Dr. SaraBuilding B

Result: Transitive dependencies are successfully eliminated. Updating an instructor's location now requires modifying a single row in the Instructors table, preventing data inconsistency.

4.5Solved Examples

📝

Consider a relation schema R(A,B,C,D,E,F) with the following set of functional dependencies F:

F={AB→C,D→E,B→F,A→D}

  1. Find all candidate keys of the relation R.

  2. Determine the highest normal form that relation R satisfies (1NF, 2NF, 3NF, or BCNF). Justify your answer.

  3. If the relation is not in 3NF,decompose it into 3NF relations.

✅ Show Solution

To determine whether the given relation R(A,B,C,D) is in Second Normal Form (2NF), let's first find the candidate keys, identify any partial dependencies, and then perform the decomposition if necessary.

Step 1: Find the Candidate Keys of R

Given the functional dependencies FD={AB→CD,B→C}:

  1. Test attribute closures:

    • Let's check AB+:

      • Start:{A,B}

      • Apply AB→CD: Add C,D→{A,B,C,D}

      • Result:{A,B,C,D}. Thus,AB is a candidate key.

    • Let's check AB subsets (A+ and B+):

      • A+={A} (cannot determine B,C,D)

      • B+={B,C} (using B→C)

Since no proper subset of AB can determine all attributes,AB is the only candidate key for relation R.

  • Prime attributes (part of a candidate key):A,B

  • Non-prime attributes:C,D

Step 2: Check for 2NF

Definition of 2NF: A relation is in 2NF if it is in 1NF and no non-prime attribute is fully functionally dependent on a proper subset of any candidate key (i.e., no partial dependencies).

Let's check the given FDs against this rule:

  1. AB→CD: This is a full dependency since the entire key AB determines CD.

  2. B→C:

    • Here,B is a proper subset of the candidate key AB (i.e.,B⊂AB).

    • C is a non-prime attribute.

    • Therefore,B→C is a partial dependency (a non-prime attribute is determined by part of the candidate key).

Conclusion:Relation R is NOT in 2NF because of the partial dependency B→C.

Step 3: Convert R into 2NF

To eliminate partial dependencies and convert the relation into 2NF, we decompose R into smaller relations:

  1. Extract the partial dependency into its own relation:

    • The determinant B and the attribute it determines (C) form the first decomposed relation:

      • R1​(B,C) with FD:B→C (where B is the primary key of R1​).

  2. Create the remaining relation with the candidate key and remaining attributes:

    • The original candidate key attributes plus any attributes not involved in the partial dependency form the second relation:

      • R2​(A,B,D) with FDs:AB→D (where AB is the primary key of R2​).

Final Result

The relation R is decomposed into the following 2NF relations:

  • R1​(B,C) with primary key B

  • R2​(A,B,D) with primary key AB

📝

Consider a relation schema R(A,B,C,D,E) with the following set of functional dependencies F:

F={AB→C,C→D,D→B}

  1. Find all candidate keys of the relation R.

  2. Determine whether R is in 3NF. If not, decompose it into 3NF.

✅ Show Solution

Step 1: Find the Candidate Keys

  1. Test attribute closures:

    • AB+:

      • Start:{A,B}

      • Apply AB→C: Add C→{A,B,C}

      • Apply C→D: Add D→{A,B,C,D}

      • Apply D→B: Add B (already there)

      • Wait, what about E? Notice that E never appears on the right-hand side of any functional dependency in F. Because E cannot be generated by any FD,E must be part of every candidate key.

    • Let's re-test ABE+:

      • Start:{A,B,E}

      • Apply AB→C→D→B→C…→ Generates {A,B,C,D,E}.

      • Result:{A,B,C,D,E}. Thus,ABE is a candidate key.

  2. Are there other candidate keys?

    • Since D→B and C→D and AB→C, we can substitute:

    • Let's check ACE+:

      • Start:{A,C,E}

      • Apply C→D: Add D→{A,C,D,E}

      • Apply D→B: Add B→{A,B,C,D,E}

      • Result:{A,B,C,D,E}. Thus,ACE is also a candidate key.

    • Let's check ADE+:

      • Start:{A,D,E}

      • Apply D→B: Add B→{A,B,D,E}

      • Apply AB→C: Add C→{A,B,C,D,E}

      • Result:{A,B,C,D,E}. Thus,ADE is also a candidate key.

Candidate Keys:ABE,ACE, and ADE.

  • Prime attributes:A,B,C,D,E(Every attribute is part of at least one candidate key!)

  • Non-prime attributes: None.

Step 2: Check for 3NF

Definition of 3NF: A relation is in 3NF if, for every functional dependency X→Y, at least one of the following holds:

  1. X→Y is a trivial functional dependency (Y⊆X).

  2. X is a superkey for R.

  3. Every attribute in Y−X is a prime attribute (part of a candidate key).

Let's test each FD in F:

  1. AB→C:AB is not a superkey, but C is a prime attribute→ Satisfies 3NF.

  2. C→D:C is NOT a superkey, and D is a prime attribute→ Satisfies 3NF!(This is the crucial edge case: even though C is not a superkey, 3NF allows this dependency because D is prime).

  3. D→B:D is NOT a superkey, and B is a prime attribute→ Satisfies 3NF.

Conclusion: Relation Ris already in 3NF because every non-trivial dependency has a right-hand side consisting of prime attributes. No decomposition is needed.

📝

Consider a relation schema R(W,X,Y,Z) with the following set of functional dependencies F:

F=WX→Y,Y→Z,Z→X

  1. Find all candidate keys of the relation R.

  2. Determine the highest normal form that relation R satisfies (1NF, 2NF, 3NF, or BCNF). Justify your answer.

✅ Show Solution

Step 1: Find the Candidate Keys

  1. Analyze the attributes to see which ones never appear on the right-hand side (RHS) of any FD:

    • RHS attributes:Y,Z,X.

    • Notice that W never appears on the right-hand side of any functional dependency. Therefore,W must be part of every candidate key.

  2. Test attribute closures starting with W:

    • W+:

      • Start:{W}

      • No FD has W alone on the LHS. Thus,W+={W} (Not a key).

    • WX+:

      • Start:{W,X}

      • Apply WX→Y: Add Y→{W,X,Y}

      • Apply Y→Z: Add Z→{W,X,Y,Z}

      • Result:{W,X,Y,Z} (All attributes!) →WX is a candidate key.

    • Alternative path using Z→X:

      • What about WZ+?

      • Start:{W,Z}

      • Apply Z→X: Add X→{W,X,Z}

      • Apply WX→Y: Add Y→{W,X,Y,Z}

      • Result:{W,X,Y,Z} (All attributes!) →WZ is also a candidate key.

Candidate Keys:WX and WZ.

  • Prime attributes:W,X,Z (attributes that belong to at least one candidate key). Wait, let's check Y:

    • Does Y belong to a candidate key? Let's check WY+:

      • Start:{W,Y}

      • Apply Y→Z: Add Z→{W,Y,Z}

      • Apply Z→X: Add X→{W,X,Y,Z}

      • Result:{W,X,Y,Z}→WY is also a candidate key!

    • All attributes (W,X,Y,Z) are prime attributes because every single one of them participates in at least one candidate key (WX,WZ, or WY).

Step 2: Determine the Highest Normal Form

Let's check each FD against the normalization rules:

  1. WX→Y:

    • WX is a candidate key (superkey) → Satisfies BCNF, 3NF, and 2NF.

  2. Y→Z:

    • Y is not a superkey.

    • However, let's check the right-hand side (Z):Z is a prime attribute (part of candidate key WZ).

    • Under the 3NF definition, a dependency where the LHS is not a superkey is still allowed in 3NF as long as the RHS attributes are prime. Therefore,Y→Z satisfies 3NF, but violates BCNF.

  3. Z→X:

    • Z is not a superkey.

    • However, the right-hand side (X) is also a prime attribute (part of candidate keys WX and WZ).

    • Therefore,Z→X satisfies 3NF, but violates BCNF.

Conclusion:

  • The relation is in 3NF because every non-trivial dependency has a right-hand side consisting of prime attributes.
